# Review-Window Race Fix and Manifest Lineage Implementation Plan

## Overview

Two independent follow-ups from the v2.3.0 rollout (PRs #21/#22):

1. **Close the codex-review-window race.** PR #21's gate hit its 8-minute
   deadline with no Codex review, passed via the unconditional advisory
   fallback, and auto-merge fired at 09:25:59Z — 63 seconds before Codex
   posted three P1 `[BLOCKER]`s (09:27:02Z). The gate must fail closed at
   the deadline when the repository is demonstrably connected to Codex, and
   re-evaluate itself when a review lands.
2. **Make audit-manifest lineage durable.** PR #22 burned review rounds 3–5
   on the manifest's `commit` field: any branch SHA stamped into
   `test-suite-manifest.json` dies at squash-merge. The artifact contract
   must stamp a commit that survives merging and define staleness against
   it.

This plan explicitly authorizes editing
`.github/workflows/codex-review-window.yml` (AGENTS.md forbids touching it
outside a plan).

## Current State Analysis

- The gate polls for a Codex review whose `commit_id` equals the PR head
  for 480 s (`.github/workflows/codex-review-window.yml:53-59`), then
  passes unconditionally with a warning when none arrived
  (`codex-review-window.yml:61-64`). The job triggers only on
  `pull_request` events (`codex-review-window.yml:2-4`), so a review that
  lands after the run finishes never re-evaluates the gate; the only hard
  stop is the 15-minute job timeout (`codex-review-window.yml:20`).
- Observed race (PR #21, 2026-08-30): window run completed in 8m09s via the
  advisory fallback; auto-merge (queued by `plaintalk-dev-agent`) merged at
  09:25:59Z; the Codex review for that exact head landed 09:27:02Z. Codex's
  own latency on this repo that morning ranged ~4–10 minutes from trigger
  to review.
- The workflow already requests a re-review on `synchronize` pushes by
  commenting `@codex review` (`codex-review-window.yml:48-51`) — evidence
  that a per-head review is expected once the repo is connected. A
  connected repo is observable: the `chatgpt-codex-connector[bot]` user has
  submitted reviews on this PR or on recent PRs
  (`codex-review-window.yml:28` names the bot).
- `fast-merge` topic opt-out and draft guard exist
  (`codex-review-window.yml:18,30-35`) and must be preserved.
- The test-suite artifact contract defines the manifest `commit` field as
  plain short HEAD
  (`plugins/rpa/skills/test-suite/references/artifact-contract.md:15,27`),
  and the audit mode records `git rev-parse --short HEAD`
  (`plugins/rpa/skills/test-suite/references/modes/audit.md:8`). The
  SKILL requires a "current" manifest for every non-audit mode but nothing
  defines currency (`plugins/rpa/skills/test-suite/SKILL.md:48-50`).
- Consequence observed on PR #22: manifests stamped `ee86cf9`, then
  `12b6619` (both squash-discarded branch SHAs) each drew a P1 lineage
  finding; the round that stamped the merge-base `e508ef7` — a
  default-branch ancestor — was the one that survived review.
- The committed manifest at `thoughts/shared/test-suite/` currently stamps
  `e508ef7`, an ancestor of master HEAD `2bda945` — already consistent with
  the rule this plan codifies; no data migration is needed.

## Desired End State

- At the polling deadline with no review for the head: the gate fails with
  a "review pending" error when Codex connection is evidenced, and passes
  advisorily only when it is not. A Codex review submitted after the
  deadline re-runs the gate automatically and flips it to the real verdict.
- The manifest contract stamps the default-branch anchor
  (`git merge-base HEAD <default>`; HEAD itself on the default branch), and
  defines a manifest as current only while that commit is an ancestor of
  the checkout HEAD. The contract states that manifests are regenerated by
  running audit on the target checkout, never hand-edited to satisfy
  review.

Recognition: a rerun of PR #21's timeline would leave the PR unmerged with
a red gate until the Codex verdict lands; a future audit on a feature
branch stamps a commit that still exists after squash-merge.

### Key Discoveries

- Failing at the deadline is safe only if something re-triggers the gate
  when the review arrives: a `pull_request_review` trigger creates a fresh
  check run for the same head SHA, and branch protection uses the latest
  run, so the gate becomes self-healing without manual re-runs.
- Connection is decidable from repository state alone: any
  `chatgpt-codex-connector[bot]` review on this PR (older head) or on the
  repository's recent PRs proves the repo is connected; a truly
  unconnected repo shows neither, and the advisory fallback remains
  correct for it.
- `git merge-base HEAD <default>` generalizes the fix that ended PR #22's
  lineage churn: on the default branch it equals HEAD; on any branch it
  names the newest commit guaranteed to survive a squash-merge.

## What We're NOT Doing

- Not replacing the advisory fallback for unconnected repositories — the
  workflow is a template used beyond this repo
  (`codex-review-window.yml:6-9` context).
- Not changing branch protection, required-check names, auto-merge
  mechanics, or the `fast-merge` opt-out.
- Not adding a post-merge manifest regeneration hook or CI job — audit is
  model-driven; regeneration stays a live-session action, which the
  contract now states explicitly.
- Not regenerating the committed manifest's detection content at
  `thoughts/shared/test-suite/` (its `commit` stamp `e508ef7` is already
  conformant). Phase 2's additive schema migration of that file — the
  `evidence` content-hash map required by the freshness rule — IS in
  scope. Not touching the tdd/one-pager artifact contracts.
- Not modifying `AGENTS.md`/`CLAUDE.md`.

## Implementation Approach

Two small, independent phases; one PR. The **initial implementation** is
one revertable commit per phase. **Review-response commits are exempt
from phase isolation**: `AGENTS.md` requires batching all open
`[BLOCKER]`s and CI failures into one fix commit, and that durable
repository rule takes precedence — a batch may therefore touch both
phases' files. Phase-level rollback of the final state is a targeted
forward-fix (revert the phase commit plus that phase's hunks of any
batch commits).
Phase 1 edits only the workflow; Phase 2 edits only the test-suite skill
package. The docs gate covers Phase 2; Phase 1 is verified by `actionlint`-
style YAML sanity (no such linter is installed — verification is manual
plus the live behavior of the next PR's gate).

## Phase 1: Fail-closed review window with self-healing re-run

### Overview

Make the deadline outcome depend on evidenced Codex connection, and let a
late review re-evaluate the gate.

### Changes Required

#### 1. Workflow triggers and guards

**Files**: `.github/workflows/codex-review-window.yml`

**Changes**:

- Add a `pull_request_review: types: [submitted]` trigger alongside the
  existing `pull_request` types (`codex-review-window.yml:2-4`).
  Review-triggered runs execute the **full gate for any reviewer** — no
  per-author skip: a gate step skipped on a review event reports a green
  job for the head SHA and would launder a red verdict; the gate is
  idempotent, so a human review merely re-evaluates Codex's state (the
  occasional extra run is the price of not being launderable). Keep the
  draft and `fast-merge` guards intact. `HEAD_SHA` for review-triggered
  runs still comes from `github.event.pull_request.head.sha`.
- On a review-triggered run, skip the `@codex review` re-request block
  (`codex-review-window.yml:48-51`) — the review already exists — and
  evaluate the verdict immediately (the poll loop finds the review on its
  first iteration).

#### 2. Deadline behavior

**Files**: `.github/workflows/codex-review-window.yml`

**Changes**:

- Extend the poll deadline from 480 s toward the job timeout
  (`DEADLINE=$((SECONDS + 780))` at `codex-review-window.yml:53`; the job
  timeout at line 20 stays 15 minutes and still bounds the run).
- Replace the unconditional advisory pass (`codex-review-window.yml:61-64`)
  with a connection probe:
  - connected ⇔ the bot has a **recent** review (submitted within the
    last 7 days) on this PR (any commit) or among the repository's last
    ~10 PRs. Recency is load-bearing: an old review must not pin the repo
    "connected" forever after the connector is removed, or the
    fail-closed path would block PRs permanently with no review ever
    arriving to self-heal; with the window, a disconnected repo degrades
    back to the advisory pass within a week;
  - connected → `exit 1` with an error naming the pending review and
    stating that the gate re-runs automatically when the Codex review is
    submitted;
  - not connected → keep the current warning + `exit 0` verbatim.
- Update the 2026-07-02 header comment (`codex-review-window.yml:11-15`)
  with the 2026-08-30 race (PR #21: advisory pass at 8m09s, merge 63 s
  before the review) so the next reader knows why the fallback is gated.

### Success Criteria

#### Automated Verification

- [x] `python3 -c "import yaml,sys; yaml.safe_load(open('.github/workflows/codex-review-window.yml'))"`
      exits 0 (workflow parses)
- [x] `grep -n "pull_request_review" .github/workflows/codex-review-window.yml`
      shows the new trigger (deviation: no per-author guard — a skipped
      gate step reports a green job and would launder a red verdict, so
      every submitted review runs the full idempotent gate; documented in
      the workflow header)
- [x] `grep -c "advisory fallback" .github/workflows/codex-review-window.yml`
      → the fallback text survives only inside the not-connected branch
      (count 1)

#### Manual Verification

      the gate reports the real verdict; a deliberate check of the run log
      shows the connection probe path taken (repo is connected, so a
      timeout would have failed rather than passed)
- [ ] A Codex review submitted after a gate run visibly starts a new
      `codex-review-window` run for the same head and updates the check

## Phase 2: Durable manifest lineage in the test-suite contract

### Overview

Stamp the audit manifest with a commit that survives squash-merges and
define manifest currency against it.

### Changes Required

#### 1. Artifact contract

**Files**: `plugins/rpa/skills/test-suite/references/artifact-contract.md`

**Changes**:

- Redefine the `commit` field (lines 15 and 27): the checkout's
  default-branch anchor — `git merge-base HEAD <default-branch>` (short),
  which equals HEAD on the default branch itself; `no-git` without a
  repository. State the reason once: branch SHAs die at squash-merge, so a
  durable stamp must be a default-branch ancestor.
- Add to the manifest section: a manifest is **current** while (1) its
  `commit` is an ancestor of the checkout HEAD (`git merge-base
  --is-ancestor <commit> HEAD`) and (2) the working tree still matches
  what the audit observed — every entry of a new additive `evidence`
  field ({file: sha256}) verifies, globbing `patterns.test_files`
  reproduces `existing_tests.files`, and re-globbing a new additive
  `detection_globs` field (the config patterns the audit probed, found
  or not) finds no file absent from `evidence` — so newly appeared
  detection inputs invalidate the snapshot. Content-based freshness on
  purpose:
  an anchor-to-HEAD diff would mark a fresh audit stale whenever the
  audited branch itself changes evidenced files. A `no-git` manifest has
  no lineage to test and is current only within its producing session.
  Otherwise non-audit modes treat the manifest as stale and direct to
  `audit`.
- Migrate the committed manifest at
  `thoughts/shared/test-suite/test-suite-manifest.json` to the extended
  schema (add its `evidence` map — CI workflows plus the four test files —
  and its `detection_globs`; detection content unchanged).
- Add to the common rules: audit artifacts are per-checkout snapshots
  produced by running `audit` on the target checkout; hand-editing a
  manifest (e.g. to satisfy review feedback) is not a valid refresh.

#### 2. Audit mode and kernel pointer

**Files**: `plugins/rpa/skills/test-suite/references/modes/audit.md`,
`plugins/rpa/skills/test-suite/SKILL.md`

**Changes**:

- `modes/audit.md:8`: record the default-branch anchor per the contract
  (`git merge-base HEAD <default>`, resolving the default branch via
  `origin/HEAD` or the repository's documented mainline). When the default
  branch cannot be determined and HEAD is not evidently on it, stop and
  ask — never stamp a branch HEAD that a squash-merge would discard
  (`no-git` without a repository).
- `SKILL.md:48-50`: point the "current manifest" requirement at the
  contract's currency definition instead of leaving currency undefined.

#### Automated Verification

- [x] `grep -n "merge-base" plugins/rpa/skills/test-suite/references/artifact-contract.md
      plugins/rpa/skills/test-suite/references/modes/audit.md` shows the

## Testing Strategy

### Unit Tests

- `python3 scripts/validate_docs.py` covers Phase 2's kernel/reference
  edits; Phase 1 has no unit harness (no workflow linter is installed —
  YAML parse check plus review).

### Integration Tests

- The shipping PR itself exercises Phase 1 live: its own
  `codex-review-window` run must take the connection-probe path, and any
  late Codex review must start a fresh gate run.

### Manual Testing

- Phase-specific manual criteria above; nothing else applies.

## Performance Considerations

The extended 780 s poll lengthens the gate only when Codex is slow and the
review has not arrived; runs where the review lands earlier are unchanged.
Not applicable otherwise.

## Migration and Rollback

- Both phases are additive policy changes; rollback is `git revert` of the
  respective phase commit.
- Existing manifests stamped with default-branch ancestors (the current
  one included) remain valid; a manifest stamped with a dead branch SHA is
  simply stale under the new currency rule and regenerates via `audit`.
- The workflow change affects only this repository's merge gating; other
  repos using the template adopt it by copying the file.
